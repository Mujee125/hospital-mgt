## 2. Life cycle model

### 2.1 Model choice

VitalFlow HMS uses an **iterative-incremental** life cycle model. Each iteration produces a potentially-shippable increment of the desktop application. Iterations are time-boxed; each delivers working Rust + TypeScript that compiles and passes the manual review gate.

### 2.2 Iteration structure

| Phase | Activities | Exit criteria |
|---|---|---|
| Plan | Pick 3–5 SRS requirements from the backlog; agree acceptance criteria | Backlog items selected; this document's relevant section updated |
| Design | Update `02-SDD-Software-Design.md` with the new component design; threat-model changes | SDD section approved by lead architect |
| Implement | Write Rust (`src-tauri/src/`) + TypeScript (`src/`); follow established patterns (RBAC + audit per command; centralised queries/models) | `tsc --noEmit` passes with zero errors; `npm run lint` passes; manual Rust review done |
| Verify | Manual review against SRS requirements; cross-check with Quality Model (`03-Quality-Model-ISO-25010.md`) | Requirements traceability table updated |
| Release | Update CHANGELOG; bump version; produce server-build and client-build installers | Installers produced on a Windows build machine; smoke-tested |

### 2.3 Iteration cadence

Two-week iterations. Phase 1 was delivered as a series of multi-agent iterations (see `/home/z/my-project/worklog.md` Tasks 0–7).

### 2.4 Tailoring

ISO/IEC/IEEE 12207 allows tailoring. The following tailoring decisions apply:

- **Acquisition process**: not formalised — the software company both builds and deploys; no external acquirer.
- **Supply process**: simplified — the software company supplies VitalFlow HMS directly to hospitals under a license agreement.
- **Some technical processes** (System Requirements Definition, System Architecture Design) are merged into the Software Requirements and Software Design processes because the "system" is the single desktop application + bundled PostgreSQL.
- **Disposal**: addressed via the data-deletion runbook in `08-Deployment-Installation-Guide.md` (decommissioning a deployment).

## 4. Configuration management

### 4.1 Version control

- **Repository**: `/home/z/my-project/hospital-mgmt/` (Git working tree).
- **Commit granularity**: one logical change per commit.
- **Branch strategy**: trunk-based for Phase 1; Phase 2 may introduce feature branches with PR review.
- **History**: `worklog.md` records the multi-agent task sequence.

### 4.2 Dependency pinning

| Artefact | Lock file | Purpose |
|---|---|---|
| Rust crates | `src-tauri/Cargo.lock` | Reproducible Rust builds |
| npm packages | `package-lock.json`, `bun.lock` | Reproducible JS builds |
| Tauri config | `src-tauri/tauri.{server,client}.conf.json` | Compile-time server/client split |

### 4.3 Database migrations

- **Location**: `src-tauri/src/db.rs::run_migrations`.
- **Properties**: idempotent (`CREATE TABLE IF NOT EXISTS`, `ADD COLUMN IF NOT EXISTS`); additive (no destructive `DROP`); re-run on every boot.
- **Rollback**: not supported — destructive schema changes are forbidden by policy. If a column must be removed, ship a migration that adds the new schema and an app update that stops writing to the old column; physical removal in a later release.
- **Seed data**: `auth::seed_defaults` re-syncs roles, permissions, and (only if zero users exist) the bootstrap admin.

## 8. Change management

### 8.1 Change classification

| Class | Definition | Approval |
|---|---|---|
| Class 1 (major) | Breaking IPC contract change; destructive schema change; license file format change; cryptographic primitive change | Sponsor + lead architect |
| Class 2 (minor) | New module/feature; additive schema change; new permission | Lead architect |
| Class 3 (patch) | Bug fix; refactoring; documentation update | Engineering peer review |

### 8.2 Change flow

1. **Request** — recorded in `worklog.md` or issue tracker.
2. **Impact analysis** — update SRS / SDD / Risk Register as needed.
3. **Approval** — per §8.1.
4. **Implement** — per iteration plan (§2.2).
5. **Verify** — per QA gates (§6).
6. **Release** — per §9.

### 8.3 Emergency changes

- Security hotfixes may bypass Class 1 approval but require retroactive sponsor notification within 24 h.
- All emergency changes are audited via `audit_logs` and recorded in `worklog.md`.

### 9.1 Build pipeline

```
Developer workstation (any OS)
   │
   ├── npx tsc --noEmit           ← TypeScript strict gate (v0.2.0 Batch 0)
   │
   ├── npm run lint               ← ESLint 9 flat config gate (v0.2.0 Batch 0)
   │
   ├── npm run format:check       ← Prettier 3 format gate (v0.2.0 Batch 0)
   │
   ├── cargo check                ← Rust gate (manual; planned CI Batch 5)
   │
   ├── cargo build --features server-build  ← Windows build machine
   │      + npm run tauri:build:server
   │      → produces VitalFlowHMS-Server-<ver>.exe
   │
   └── cargo build --features client-build  ← Windows build machine
          + npm run tauri:build:client
          → produces VitalFlowHMS-Client-<ver>.exe
```

> **v0.2.0 note:** every `npm run build*` script invokes `tsc --noEmit` before `vite build`, so the TS gate cannot be skipped. `npm run lint` and `npm run format:check` are wired into the same scripts via the `&&` operator. The CI runner that automates `cargo check`/`cargo audit`/`npm audit` on every push is **Planned Batch 5**.

### 9.2 Release artefacts

| Artefact | Description |
|---|---|
| `VitalFlowHMS-Server-<ver>.exe` | NSIS installer with bundled PostgreSQL; `installMode: perMachine` |
| `VitalFlowHMS-Client-<ver>.exe` | NSIS installer without PostgreSQL; distinct product name/identifier |
| `license.json` (per hospital) | Ed25519-signed license file produced offline by the software company |
| Release notes | CHANGELOG entry; updated `worklog.md` |

### 9.3 Deployment model

See `08-Deployment-Installation-Guide.md` for the full procedure. Summary:

1. Run server installer on the designated server PC (auto-provisions PostgreSQL as a Windows Service).
2. Boot the HMS app on the server PC; first-run admin credentials are randomly generated (24-char CSPRNG) and written to `%ProgramData%\HMS\bootstrap-credentials.txt` (ACL: SYSTEM + Administrators only). The operator reads the file, logs in as `admin` with that one-time password, and is forced to change it (CR-2, Batch 1). The Phase 1 hardcoded `admin/ChangeMe123!` pair is removed.
3. Issue a license: copy the server's hardware fingerprint (Settings → License), send to the software company, receive `license.json`, drop at `C:\ProgramData\HMS\license.json`, restart.
4. Run client installer on each client PC; first-run Setup screen: enter server IP + pairing code (generated on the server's Settings → "Connect a New Client PC").
5. Verify post-install checklist (`08-Deployment-Installation-Guide.md` §11).

### 9.4 Upgrade path

- **Server upgrade**: rerun the new server installer. `NSIS_HOOK_POSTINSTALL` detects existing `pgdata\PG_VERSION` and skips re-initdb. Idempotent migrations apply new schema on next boot.
- **Client upgrade**: rerun the new client installer. Config (`config.json`) is preserved.
- **License upgrade**: Settings → License → Install new license, or replace `C:\ProgramData\HMS\license.json` and restart.
- **License renewal (expiry or hardware change)**: see `07-Licensing-Architecture.md` §10 (runbook).

### 9.5 Rollback

- **App rollback**: reinstall the previous-version installer. The DB schema is forward-compatible-additive, so older app code reads new columns as NULL safely.
- **DB rollback**: restore from `pg_dump` (per `08-Deployment-Installation-Guide.md` §8). Destructive schema changes are forbidden by policy, so DB rollback is rarely needed.
- **License rollback**: not supported — once a license is installed, it remains until replaced. If a new license is rejected, the old one (if still on disk in a backup location) can be re-installed via `install_license`.
